# StockFlow 库存核心规则

> 版本：v1.0 ｜ 本文档是库存数据正确性的唯一依据，变更属于重大变更 ｜ 关联文档：[business-flow](business-flow.md)、[architecture](architecture.md)

---

## 1. 库存的最高原则

库存是整个系统最重要的数据。

**硬性约束**：

1. 禁止通过 `UPDATE inventory SET quantity = ...` 直接修改库存。
2. 所有库存变化必须来源于业务动作（入库、出库、调拨、盘点调整、库存调整单等）。
3. 任何库存变化必须同步生成库存流水，且二者在同一事务中（见 architecture.md §4）。
4. 库存数字计算只发生在后端（Service/Repository 层），前端禁止自行计算库存。

---

## 2. 库存模型（状态维度）

库存至少区分以下状态：

```text
总库存
可用库存      = 总库存 - 锁定 - 冻结 - 待检 - 不良品 - 其他不可用
锁定库存      订单占用/盘点锁定等
冻结库存      质检冻结/人工冻结/异常冻结
待检库存      质检中
不良品库存    质检不合格转入
在途库存      调拨在途/采购在途
```

> **注（M2 在途口径，backend-m2-plan §6.6）**：M2 的实时"在途库存"= **调拨单聚合口径**（调拨单已出库执行、入库执行未完成的数量，按 SKU/目标仓聚合）；采购在途（已审核未收齐采购订单）不在 inventory 六状态内体现，属单据域聚合查询。调拨出库执行即扣源仓 total、目标仓不入账，入库执行时补入——两端流水成对、在途由调拨单状态承载。

**一致性恒等式**（所有时刻、所有代码路径都必须满足）：

```text
总库存 = 可用 + 锁定 + 冻结 + 待检 + 不良品 + 其他不可用状态之和
```

任何库存操作后必须保证恒等式成立，测试必须覆盖（见 testing.md）。

---

## 3. 库存定位维度

库存记录最少能够定位到五维：

```text
SKU + 仓库(warehouse) + 库位(bin) + 批次(batch) + 序列号(serial)
```

底层数据库从一开始就支持多仓，库存表必须包含：

```text
sku_id + warehouse_id + zone_id + shelf_id + bin_id (+ batch_id + serial_id)
```

禁止把库存设计成 `sku_id + quantity` 的简单结构。

---

## 4. 库存锁定

支持的锁定类型：

```text
订单占用（销售订单审核后预占）
盘点锁定（盘点冻结范围内库存）
质检冻结（待检库存）
人工冻结（管理员手动）
异常冻结（异常单触发）
```

锁定的目的：**防止库存被两个订单重复使用（超卖）**。

锁定规则：

1. 锁定必须记录：来源单据、锁定类型、锁定数量、操作人、时间。
2. 释放锁定必须由明确的业务动作触发（发货扣减、订单取消、盘点结束等），并生成流水。
3. 可用库存 = 总库存 − 所有有效锁定/冻结；分配与预占只允许使用可用库存。

---

## 5. 库存流水（Ledger）

每一次库存变化都必须生成一条库存流水。

流水字段：

```text
流水号
SKU、仓库、库位、批次、序列号
变化前数量、变化数量、变化后数量
业务类型（入库/出库/调拨/盘点调整/调整单/...）
业务单号（来源单据）
操作人、操作时间、备注
```

**规则**：

1. 流水只增不改不删（append-only），任何库存调整都能够通过流水追溯来源。
2. 流水与库存变更在同一数据库事务中提交。
3. 流水属于审计数据，普通管理员不可修改（见 database.md §7）。

---

## 6. 批次管理

启用批次管理的 SKU，库存必须按批次维度记录。

批次字段：

```text
批次号、生产日期、入库日期、有效期、供应商、成本价、当前库存
```

批次在入库（收货/质检/上架）环节采集，在出库分配环节被策略命中（FIFO/FEFO）。

---

## 7. 效期管理

### 7.1 预警阈值

支持可配置的临期阈值：

```text
30天、15天、7天、3天、已过期
```

### 7.2 功能要求

```text
临期预警、过期预警（通知中心 + 库存预警页面）
临期库存查询、过期库存查询
FEFO 出库（先到期先出，作为出库分配策略）
```

效期预警扫描由定时任务驱动（见 architecture.md §9）。

---

## 8. 序列号管理

适用于手机、电脑、设备、电子产品、仪器等单品管理场景。

**规则**：

1. 序列号全局唯一。
2. 启用序列号管理的 SKU，入库/出库/盘点必须逐个序列号操作。

   > **注（M2 逐件落地口径，backend-m2-plan §6.2/§6.7/§6.9）**：收货按件采集序列号并 SerialEvent 建档（IN_STOCK 于指定库位）；盘点冻结时对序列号 SKU 建档 count_items 序列号级明细（qty_system=1）并逐件 SerialEvent(FROZEN)，完成时按实盘联动——缺失核销 OUTBOUND、多出建档 IN_STOCK、无差异回位（source=调整单/盘点单）；出库侧（销售发货、采购退货出库）出库前逐件校验台账（存在 + 属该 SKU + IN_STOCK + 位于指定库位）后 SerialEvent(OUTBOUND)，序列号台账与库存数量同事务变更。
3. 记录完整生命周期：

```text
采购 → 入库 → 库位 → 调拨 → 盘点 → 出库 → 客户 → 退货
```

序列号每次状态变化都记录：来源单据、位置、操作人、时间。

## 9. 库存并发控制（核心）

### 9.1 典型场景

```text
用户 A 正在出库 10，用户 B 同时出库 10，实际只有 15
```

系统不能产生负库存或超卖。

### 9.2 后端必备机制

```text
事务（Transaction）
行级锁或等价机制（SELECT ... FOR UPDATE / 乐观锁版本号 / 原子 UPDATE 条件更新）
原子更新（带条件的 UPDATE ... WHERE available >= n）
库存校验（业务层 + 数据层双重校验）
幂等（重复请求不重复扣减，见 architecture.md §3）
并发保护（任务领取、盘点并发的互斥）
```

### 9.3 实现要求

1. 扣减库存必须使用原子操作（如 `UPDATE inventory SET locked = locked + n WHERE id = ? AND total - locked >= n`），影响行数为 0 即视为库存不足并回滚。
2. 关键操作的事务边界见 architecture.md §4。
3. 并发场景必须有集成测试覆盖（见 testing.md §4）。

## 10. 库存追溯

任何 SKU 可以查看完整追溯链：

```text
库存当前状态 → 当前库位 → 批次 → 入库来源（采购订单）
→ 调拨记录 → 出库记录 → 退货记录
```

序列号支持完整生命周期追溯（见 §8）。

追溯数据来源：库存流水 + 业务单据 + 操作日志，构成完整审计链（见 testing.md 与 requirements.md 交付标准）。

## 11. 库存智能能力（增强模块）

| 能力 | 输入 | 输出 |
|---|---|---|
| 智能补货 | 历史销量、当前库存、安全库存、采购周期、最近出库量 | 建议补货数量 |
| 库存预测 | 历史出入库数据 | 未来 7 天 / 30 天库存变化 |
| 库位推荐 | 容量、SKU 属性、已有库位、批次、拣货需求 | 推荐上架库位 |
| 积压识别 | 最近移动时间 | 30/60/90 天未动库存清单 |

智能能力为辅助决策模块，其建议必须可追溯计算依据，且不自动改变任何库存与单据状态。
