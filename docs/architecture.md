# StockFlow 系统架构与工程规范

> 版本：v1.0 ｜ 后端工程规范 ｜ 关联文档：[inventory-rules](inventory-rules.md)、[api](api.md)、[database](database.md)

---

## 1. 分层架构

所有功能必须形成完整链路：

```text
前端 → API → Service → Repository → Database
```

- **API 层**：参数接收与基础校验、认证鉴权、Request ID 透传、统一响应封装。
- **Service 层**：业务逻辑、状态机、事务边界、权限校验、库存校验。
- **Repository 层**：数据访问，禁止出现业务判断。
- **禁止**：Controller 直接操作数据库；前端参与业务计算。

## 2. 统一错误处理

### 2.1 错误响应结构（全后端统一）

```json
{
  "code": "INVENTORY_NOT_ENOUGH",
  "message": "库存不足",
  "request_id": "xxx",
  "details": {}
}
```

- `code`：机器可读错误码，按模块划分命名空间（如 `INVENTORY_*`、`AUTH_*`、`DOC_*`）。
- `message`：用户可理解的信息。
- `request_id`：请求追踪 ID。
- `details`：结构化补充信息（如具体哪个 SKU 不足）。

前端根据错误码展示用户可理解的信息，错误码清单在 api.md 维护。

## 3. Request ID 与幂等

### 3.1 Request ID

每一个请求必须携带/生成 `request_id`：

```text
前端报错 → 携带 request_id → 查日志 → 找到请求 → 定位后端问题
```

后端中间件统一处理：接受前端传入的 request_id 或自动生成，写入响应头并贯穿整条日志链。

### 3.2 幂等要求

以下请求必须支持幂等：

```text
收货、入库、出库、库存调整、调拨、盘点、发货、支付式确认操作
```

用户连续点击两次，不能执行两次库存变化。

实现方式（按场景选择）：

- 前端提交时携带幂等键（Idempotency-Key），后端按键去重。
- 单据状态机天然幂等（重复提交同状态迁移直接返回成功或明确冲突）。
- 关键库存动作以业务单据 + 行号作为去重依据。

## 4. 事务边界

以下操作必须放在可靠事务中：

```text
订单状态变化
库存变化
库存流水写入
业务流水写入
```

标准事务示例（出库发货）：

```text
BEGIN
  扣减库存（原子 UPDATE + 行锁）
  写库存流水
  更新出库单状态
  更新拣货任务状态
  释放/核销库存锁定
  写操作日志
COMMIT
```

任何关键步骤失败，整体回滚。

### 4.1 异常恢复

真实生产系统不能因为一个错误就把状态搞乱：

- 场景："扣库存成功、写日志失败" —— 必须在同一事务中，保证整体回滚或可靠补偿，做到最终一致。
- 场景："Excel 已生成但下载失败" —— 文件保留有效期，用户可重新下载（见 excel.md §5）。

## 5. 并发与锁

必须设计以下并发场景的处理：

```text
库存并发（同一 SKU 同时出库）
订单并发（同一订单同时操作）
任务领取（两个员工同时领取同一任务）
盘点并发（多人同时盘同一范围）
重复提交（网络重试导致的重复请求）
重复扫码（PDA 连续扫同一码）
```

实现要求：

1. 库存：见 inventory-rules.md §9。
2. 任务领取：使用原子抢占（`UPDATE task SET assignee=? WHERE id=? AND status='PENDING'`），影响行数为 0 即领取失败并明确提示。
3. 任务状态机：`待分配 → 已分配 → 处理中 → 已完成`，只能被合法用户（角色 + 仓库权限）领取；支持转派、释放、重新分配。
4. 任务超时：记录创建时间、领取时间、开始时间、完成时间、超时时间；后台定时任务识别超时任务并告警。

## 6. 生产安全（后端）

至少实现：

```text
密码哈希（bcrypt/argon2，禁止明文与弱哈希）
JWT 安全（签名、过期、刷新机制）
CORS 白名单
请求校验（所有输入）
权限校验（API 级别，不只靠前端）
SQL 注入防护（参数化查询/ORM）
XSS 防护
CSRF 风险控制
文件上传校验（见 api.md §5）
登录保护（见 permission.md）
敏感信息脱敏（日志、响应中的手机号/邮箱等）
```

**日志红线**：日志中禁止打印密码、Token、敏感密钥。

---

## 7. 性能要求

重点列表必须支持：分页、索引、条件查询、批量操作、懒加载、缓存。

避免：

```text
N+1 查询
无条件 SELECT *
一次查询几百万行
循环中连续查询数据库
```

具体措施：列表接口强制分页；高频查询字段建索引；详情接口批量装配关联数据；报表走汇总表或异步任务。

---

## 8. 生产日志体系

系统日志分类：

```text
业务日志、错误日志、访问日志、审计日志
定时任务日志、导入日志、导出日志、打印日志
```

### 8.1 操作日志

必须记录：

```text
用户、IP、设备、时间、模块、对象、动作、请求、结果
```

对关键更新保存**修改前/修改后**快照。

重点审计对象：

```text
库存、权限、单据、价格、库存调整、盘点、用户、系统配置
```

### 8.2 操作日志查询

支持按：用户、模块、时间、IP、操作类型、成功/失败 筛选；支持详情查看完整变更内容。

### 8.3 审计链

所有关键业务必须形成：

```text
业务单据 + 库存流水 + 操作日志 + 状态记录
```

形成完整审计链，支撑追溯与追责（详见 database.md §7、inventory-rules.md §10）。

---

## 9. 定时任务

### 9.1 任务清单

```text
库存预警扫描、效期预警扫描、长期库存扫描
数据统计、报表汇总、异常检测
日志清理、临时文件清理
```

### 9.2 任务管理要求

- 支持配置执行时间（cron）、启用/停用。
- 每次执行记录执行日志（开始/结束/结果/耗时）。
- 失败重试机制 + 失败告警（见 deployment.md §5）。
- 任务执行幂等，防止重复触发造成重复预警/重复扣减。

---

## 10. 通知中心

```text
通知类型：系统通知、审批通知、库存预警、效期预警、异常通知、任务通知
状态管理：未读 / 已读 / 全部已读
```

通知由业务事件驱动（单据审批、预警扫描、异常创建、任务分派），存储于通知表，前端提供未读数与通知列表。

## 11. 技术栈与选型

### 11.1 选型决策

| 层 | 决策 |
|---|---|
| 后端语言 | **Go**（goroutine 并发模型，契合仓库作业高并发、低延迟要求） |
| 后端库 | 按 **高并发、低延迟** 导向选型（见 §11.2） |
| 前端 | **React 18+ + Ant Design 6**（最新稳定版，https://ant.design/index-cn），见 §11.3 |

以下为项目基线选型。替换任何一项必须先评估生态兼容与维护性，并在本文档与 changelog 中记录。

### 11.2 后端选型清单（Go，高并发低延迟导向）

| 领域 | 选型 | 说明 |
|---|---|---|
| HTTP 框架 | **Gin** | 高性能 radix tree 路由、中间件生态最全；对整体延迟而言，DB/缓存设计的影响远大于框架层差异 |
| 数据库 | **PostgreSQL 15+**（驱动 **pgx**） | 强事务、行级锁（`FOR UPDATE`）、高并发写入下 MVCC 表现好，契合库存强一致性场景；团队更熟悉时可换 MySQL 8（go-sql-driver），文档其余部分均以抽象表述不受影响 |
| 数据访问 | **GORM** 为主 + 库存关键路径**原生 SQL** | 库存扣减/锁定等热点操作用原子 UPDATE 与行锁精确控制（inventory-rules.md §9） |
| 缓存 | **go-redis v9** | 连接池 + Pipeline；热点库存/字典/权限缓存 |
| 日志 | **zap** | 零分配结构化日志，满足 §8 分类日志要求 |
| JSON 序列化 | **bytedance/sonic**（可选） | 兼容标准库 API，高吞吐下降低序列化延迟 |
| 协程池 | **panjf2000/ants** | 批量导入/导出等场景控制 goroutine 数量 |
| 异步任务队列 | **asynq**（基于 Redis） | 导入/导出/打印任务、任务进度上报（excel.md §3–4） |
| 定时任务 | **robfig/cron**（+ asynq periodic） | 预警扫描、报表汇总等（§9） |
| 实时通知 | SSE（默认）/ **gorilla/websocket** | 通知中心推送（§10） |
| 配置 | **viper** | 环境变量 + 配置文件 + Secret（deployment.md §1） |
| 参数校验 | **go-playground/validator** | Gin 原生集成，配合业务校验（api.md §4） |
| 认证 | **golang-jwt/v5** + **x/crypto**（bcrypt/argon2） | permission.md §3 |
| Excel | **excelize** | 流式读写，支撑大数据量导出（excel.md §3） |
| 条码生成 | **boombuler/barcode** | Code128/QR 后端批量生成；前端渲染见 §11.3 |
| API 文档 | **swaggo/swag** | 注释生成 OpenAPI（api.md §3） |
| 数据库迁移 | **golang-migrate** | database.md §9 |
| 测试 | **testify** + **testcontainers-go** | 单元测试 + 真实依赖集成测试（testing.md） |

| 客户端状态 | zustand | 登录态、全局设置 |

### 11.4 性能配置底线

1. 数据库/Redis 连接池参数必须显式配置并纳入配置管理（最大连接数、空闲连接、连接生命周期），禁止使用默认值上线。
2. 高频接口（库存查询、扫码解析、作业确认）走缓存与索引优化路径，遵循 §7 性能要求。
3. 异步任务（导入/导出/打印）必须可观测：队列长度、进度、失败重试可见（excel.md §4、deployment.md §5）。

### 11.5 其他约定

- 引入新依赖必须评估维护性与生产可用性，避免引入与基线功能重叠的库。
- 配置管理遵循 deployment.md（环境变量 + 配置文件 + Secret，禁止写死）。
